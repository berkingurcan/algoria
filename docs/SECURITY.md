# Security model

## Wallet and sessions

- Authentication uses SEP-10 with the passphrase of the network the deployment is pinned to, so a challenge issued by one deployment cannot be replayed against the other.
- Challenges expire after five minutes and are consumed atomically by transaction hash to prevent replay.
- Access tokens last 15 minutes; refresh sessions last seven days and are stored as HMAC hashes.
- Both cookies are HttpOnly and SameSite=Lax; production HTTPS makes them Secure.
- Algoria JWTs are verified only by Algoria. They carry Algoria's own audience and no `role` claim, so the session cookie is not a Supabase-shaped token and cannot become a database credential even where the signing secret is misconfigured to match the project's. Server-side Supabase queries explicitly bind the authenticated wallet user's UUID; RLS remains defense in depth and no custom Algoria JWT is passed to PostgREST as a Supabase Auth token.
- `ALGORIA_JWT_SECRET` is an independent secret. It must never be set to the Supabase project's JWT secret.

## Network and feature policy

- One deployment serves exactly one network. `PUBLIC_STELLAR_NETWORK` selects the profile, and every request re-derives it from the installed Stellar, x402, and Stellar 8004 SDKs, so a drifted or wrong value fails closed instead of pointing real value at the wrong chain.
- API routes fail with `503 network-policy-mismatch` when deployment variables attempt another network, RPC, or payment cap.
- Public Bazaar routing, runtime MCP, MPP, A2A, and open catalog search are disabled and fail with `501 unsupported-policy`.
- Mainnet execution and on-chain feedback are open. Each was opened only once it had something real behind it, and each stays gated by the same policy check that refuses the rest.
- Only operator-allowlisted Stellar 8004 identities declaring HTTP, optionally x402, are eligible.

## Agent execution

- Browser-submitted resource objects are never authoritative. The server re-resolves the allowlisted 8004 identity and requires its endpoint to match.
- External endpoints must use HTTPS, the default port, no embedded credentials, and public destinations. Redirects are followed manually and revalidated. Node uses DNS-pinned Undici; Cloudflare Workers use the platform's public-Internet-only outbound proxy with `global_fetch_strictly_public`.
- Private, loopback, link-local, documentation, multicast, and reserved address ranges are blocked.
- Active HTTP response bodies are bounded to 1 MiB while streaming and calls have timeouts.
- Agent metadata and request schemas are untrusted data, never model instructions.
- Job approval authorizes exactly the reviewed immutable request snapshot; it does not authorize future calls.
- Every controlled-provider request carries a random recovery token. Supabase stores only its SHA-256 hash, and status/replay responses use a constant-time comparison before returning the Artifact or receipt.
- The signed immutable snapshot binds recovery to the provider's same origin and exact correlation path. Recovery-token requests may not redirect, so the bearer token is not forwarded to another host.

## Payments

- Only exact x402 payments in the USDC Stellar Asset Contract pinned by the deployment's own network profile are accepted.
- The USDC SAC is `CBIELTK6YBZJU5UP2WWQEUCYKLPU6AUNZ2BQ4WWFEIE3USCIHMXQDAMA` on testnet and `CCW67TSZV3SSS2HXMBQ5JFGCKJNXKZM7UQUWUZPUTHXSTZLEO7SJMI75` on mainnet.
- The per-payment cap is a ceiling, not a setting. The compiled-in ceiling is 1 USDC; an operator may tighten it by configuration but can never raise it, and a value above it is refused at startup. The testnet deployment runs at `1`, the mainnet deployment at `0.1`.
- Network, asset, atomic amount, recipient, expiry, scheme, and quote identity are checked before signing and again before egress. The payment route additionally verifies that the stored challenge still hashes to the recorded quote hash before accepting a credential.
- A facilitator's settlement claim is not proof. Every claimed receipt is re-derived from the ledger before it is recorded: the transaction must exist, have succeeded, and contain a transfer of the approved amount to the approved recipient in the pinned asset, where the asset is matched by deriving its SAC from the ledger's own code/issuer pair rather than by trusting a label. A claim that does not verify stays `reconciling` for operator review instead of becoming a receipt; Artifact delivery is independent of settlement proof, so the user still receives the work.
- The per-payment cap bounds one signature, so a rolling per-wallet ceiling bounds a run of them. Signed, reconciling, and settled payments all consume that budget, so an unresolved outcome cannot be retried around. `MAX_PAYMENT_USDC` is a ceiling an operator may tighten but never raise.
- Payment review states plainly when a service exposes no status lookup, because a lost response from such a service cannot be re-fetched. The ledger check still answers whether the payment settled.
- The paid retry uses the stored request snapshot, not new browser input.
- Quotes are short-lived and claimed through an atomic transition to prevent reuse.
- Payment approval is separate from job approval.
- A successful controlled-provider correlation id is replay-safe: the same work returns its stored Artifact without another facilitator call. Rebinding it to different work returns `409`.
- Algoria consumes controlled-provider recovery after a lost paid response. It marks the Job complete only when recovery includes a settled Payment Receipt; a bare `200` response without settlement evidence remains uncertain.
- The user can re-drive that same recovery lookup later through `POST /api/jobs/{id}/recover` (authenticated, owner-scoped). It reuses the immutable snapshot's recovery URL and token, never resubmits a payment credential, applies success only with settlement evidence, and moves a claimed-but-lost payment into the visible `payment-uncertain` state instead of leaving it silently `executing`. `GET /api/jobs/{id}` exposes the authoritative Job state so the client never has to guess after an ambiguous outcome.
- Facilitator timeout is an indeterminate settlement outcome, not a failed payment. The provider records `uncertain`, exposes the exact bounded status, and prevents blind repayment. Lean v0 does not pretend an automatic reconciler exists; operator review is required for this rare state.
- Operator review has a concrete tool: `pnpm ops:uncertain` lists every `payment-uncertain` Job and stale claimed `executing` Job, re-drives the same bounded status lookup with the stored recovery token, and with `--apply` writes only evidence-backed outcomes (settled receipt → succeeded, recorded terminal failure → failed). Everything else stays visibly uncertain, and no payment credential is ever resubmitted. The same sweep re-checks every unverified `reconciling` receipt against the ledger and promotes it only when the approved transfer is found.

Testnet assets have no intended real-world value, but wallet signatures and payment state are still treated as security-sensitive because the same protocol design may later be promoted.

## Public repository posture

This repository is public, so it is written to be safe to read. Nothing here depends on the source staying hidden.

- Every value committed in `wrangler.jsonc` and `.env.example` is public by design: the app origin, the Supabase project URL, the Supabase publishable key, the payee G-address, allowlisted agent ids, the network profile, and the operator-authored request shapes. Secrets live only in Wrangler secrets, CI secrets, and a gitignored `.env`: `SUPABASE_SECRET_KEY`, `SEP10_SIGNING_SECRET`, `ALGORIA_JWT_SECRET`, `ALGORIA_SESSION_PEPPER`, and any wallet key. They have never been committed; CI also scans the full history with gitleaks on every push.
- The publishable key grants the `anon` role, and `anon` holds no table privileges at all (`revoke all on all tables in schema public from anon, authenticated`, migration 0003), with row level security enabled on every table. Verified against the deployed project: a direct PostgREST read of `app_users`, `conversations`, `messages`, `jobs`, `payment_records`, `sep10_challenges`, `auth_sessions`, `audit_events`, and `provider_runs` with that key returns `42501` insufficient privilege on all of them. Server-side access uses the secret key and binds the authenticated wallet's UUID explicitly.
- The SEP-10 server signing key's public address is published in `/.well-known/stellar.toml` on purpose; its secret is not in the repository, and testnet and mainnet use different keys.
- `ALGORIA_PROVIDER_TEST_TOKEN` enables the adversarial `response-loss` mode, which settles a payment and then deliberately withholds the response. It ships inert, because the code path is unreachable unless the variable is set, and it must never be set on a deployment that handles real value.
- Publishing the source also publishes the exact validation rules, caps, and allowlist. That is intended: every control here is enforced server-side and re-derived from the ledger or the registry, never from a client claim or a hidden constant.
- Publishing the source also publishes the schema, so the boundaries that held by arrangement were made to hold by constraint in migration 0011. Applying it is a deployment step like any other migration, so the guarantees below describe a deployment that has run it. Row level security is forced on every table rather than merely enabled, so not even the owning role is exempt. That has a precondition worth naming: the three `security definer` functions run as the table owner, so the owner must hold `BYPASSRLS` or they would quietly match zero rows. On Supabase it does, and the migration says so rather than assuming it. Default privileges in `public` now revoke from `anon` and `authenticated` for the role migrations run as, so a table added by a future migration is not reachable with the published key before anyone remembers to revoke it; the platform keeps its own default under an admin role that a migration cannot alter, which is why the per-table revokes stay as the backstop. `authenticated` keeps only read access: the write grants on `conversations` and `messages` were unused, because this application has no browser Supabase client and the publishable key is read by no code. While they stood, an accepted token could have written a message asserting a finished job and a settled payment.
- Routing is open to a signed-out visitor because seeing what Algoria would do is the point of the landing page, but the model call behind it is not. Ranking for an anonymous caller is deterministic and local, and reaching the model is opt-in in the code rather than opt-out, so a route added later does not reach it by saying nothing. Stated honestly, this bounds *who* spends and not *how much*: SEP-10 authenticates any valid keypair, funded or not, so a session is cheap to obtain. What bounds the rate is a dedicated 20/minute bucket on that route. A per-session model budget is the control that would bound the spend itself, and this deployment does not have one yet.
- Supabase's own linter reports `rls_enabled_no_policy` on `auth_sessions`, `provider_runs`, and `sep10_challenges` at INFO level. That is the intended state, not an omission: row level security is on and no policy grants anything, so those tables deny every request that arrives with the publishable key. They are reached only by the server, with the secret key, which bypasses RLS by design. The linter flags the pattern because it is usually an accident; here it is the deny-all it looks like.
- A public repository also publishes its dependency alerts, so they are assessed rather than left open. The standing one is `elliptic` (low, no patched release), reached only through `@creit.tech/stellar-wallets-kit` → Trezor and NEAR connectors. It is absent from the built client bundle, as are `trezor` and `near-api`; the single `secp256k1` occurrence is a Soroban host-function name in the Stellar SDK's enum, not a call into the vulnerable code. Stellar signs with ed25519 throughout. Re-check this if the wallet kit's connector set changes.

## Abuse and operational limits

- API routes use bounded per-instance request limits. `/api/health` is bounded too, on a bucket generous enough for a monitor, and its schema probe is cached rather than re-queried per request, so polling it cannot spend the database's quota. `/.well-known/stellar.toml` is bounded too, because it derives a keypair per request and nothing caches it. The root page is deliberately left unbounded: its registry crawl is already bounded by a shared cache with singleflight, and a per-address limit there would be shared by everyone behind one NAT while answering a browser navigation with a JSON error body.
- Every route that accepts a JSON body bounds it before parsing rather than after, including the ones that take no session: the controlled provider, the router, and both SEP-10 steps.
- JSON request bodies are streamed through a 128 KiB application limit before parsing.
- Two different limits are easy to conflate, so they are stated apart. What bounds *spending* is durable: the per-wallet ceiling is a query over `payment_records` scoped to the wallet and the deployment's network, counting every payment that left the browser, signed, reconciling or settled alike, so an unresolved outcome still consumes the budget it might have spent. It does not depend on which isolate serves a request. What is isolate-local is the *request-rate* limiter, which bounds compute and probing rather than money, and on Workers is therefore a soft limit. Cloudflare distributed rate-limit rules remain an operator step for the public deployment; without them a determined caller gets more requests than the table suggests, but not more of anyone's USDC.
- Stellar 8004 identity and declared metadata are not proof of service quality, availability, or safe behavior.
- Mainnet runs as a separate deployment on its own origin, with its own signing key, JWT secret, and session pepper, a `0.1` USDC per-payment cap, and an allowlist naming individual routes rather than whole agents. It shares one Supabase project with testnet by decision: every row carries its network, spend ceilings count per network, and settlement is verified against that network's own Horizon, so a testnet record can neither raise a mainnet limit nor stand in for a mainnet payment. The distinct JWT secret is what keeps a testnet session from authenticating there.
